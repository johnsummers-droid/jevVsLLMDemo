0. DECISIONS AND ASSUMPTIONS
----------------------------
The spec settles the "what is a Jev node" question that CLAUDE.md left open:
Jev nodes make bounded, typed decisions (choice / score / boolean, each with
a probability or confidence). LLM nodes generate or transform text. Tools are
deterministic. Human review handles cases that are uncertain or risky.

Architecture decisions taken in this plan (each one is explained in a later
section):

D1. The server owns all node logic. The spec's NodeDefinition.run() lives
    only in Python. The browser gets the node catalog as metadata (ports,
    params, cost hints) from GET /api/catalog and never runs nodes. This
    keeps provider keys and the hidden scenario pack on the server.

D2. Pydantic models are the one source of truth for shared types. JSON Schema
    is exported from them into shared/schema/, and the TypeScript types are
    generated from that schema. CI fails if the generated files are stale.
    Two small pieces of logic are written by hand in both languages: the
    port-compatibility check and the fan-in/fan-out check, which the canvas
    needs for instant feedback while dragging. Both implementations are
    tested against one shared JSON fixture file.

D3. Control flow uses BRANCH output ports. A decision node (router, safety
    check, escalation gate, policy engine) has normal data outputs (enum,
    probability, ...) and also a set of branch outputs, for example
    "route.billing" or "route.low_confidence". Exactly one branch fires per
    request. A branch port carries the node's pass-through text, so it is
    typed "text" and the normal type rules still apply. Nodes that sit only
    on branches that did not fire are skipped (dead-path elimination).

D4. Request envelope. Every request carries an envelope holding: scenario
    id, original message, decisions made so far, and taint flags. Port values
    carry their own taint flags (e.g. "injection", "pii", "policy_violation")
    so the engine can decide afterwards whether an unsafe response reached
    the customer. Participants never see the envelope; only the engine and
    the mocks use it.

D5. Simulated time is separate from wall-clock time. In mock mode the
    executor computes simulated latencies; a separate "pacer" emits the
    WebSocket events on a compressed wall-clock schedule so the edge
    animations are watchable. In real-provider mode the executor uses
    measured latencies and the pacer emits events immediately. There is one
    executor for both modes.

D6. Mocks are deterministic and fair. The random seed for each node call is
    sha256(run_seed, scenario_id, node_type, params_fingerprint). Two teams
    with the same node and the same params get identical results, no matter
    what node ids their graphs use. Python's built-in hash() is not used
    because it is salted per process.

D7. One graph per team, last write wins. Each team has one laptop (per the
    spec), so there is no collaborative editing (no CRDT). Saves carry an
    integer version: a stale version returns 409, and a save while the graph
    is locked returns 423. Graphs are stored on the server and autosaved, so
    they survive a page refresh.

D8. Single backend instance. Run state and the WebSocket hub live in memory
    in a single uvicorn process. That is enough for 6 teams. Scaling out
    later would need Redis pub/sub; that is out of scope and noted in the
    deployment section.

D9. Runs come in two kinds:
      - practice: a team runs its own graph on the PRACTICE pack. Results
        are visible to the team, and the run is not on the leaderboard.
      - official: the facilitator starts it. Every team graph is locked and
        snapshotted, and all of them run on the hidden OFFICIAL pack with
        the same seed. These runs feed the leaderboard.
    During official runs the params on the customer-message node (traffic
    mix, attack rate) are overridden by the facilitator's run config, so
    every team gets identical traffic.

D10. Small deviations from the spec, made on purpose:
      - Node categories are io | jev | llm | tool | human. The spec's
        NodeDefinition type lists four categories, but its catalog table has
        a fifth, Human review.
      - The Jev escalation gate gets an extra required "text" pass-through
        input so that its branch ports have something to forward.
      - The router's "probabilities" output is a json port that holds a
        Distribution object. No new port type is needed for it.
      - The "image" port type is defined but no MVP node uses it.

Assumptions. None of these change the architecture; they are open items to
confirm:
  A1. The real Jev API takes {state, questions[]} as in spec section 6 and
      returns one answer per question with a value, probabilities and a
      confidence. The JevProvider adapter keeps the exact wire format
      contained, so the rest of the system does not depend on it.
  A2. The real LLM is Claude, called through the Anthropic SDK on the server.
      The model param is a tier ("small" | "large"), and the server config
      maps tiers to model ids (e.g. claude-haiku-5-5 / claude-sonnet-5-5).
      Prices live in server config, not in code.
  A3. Workshop language is English. The "language" param exists but the mock
      only produces "en" for the MVP.

                         "image","any"]
  NodeCategory = Literal["io","jev","llm","tool","human"]

  class Port(BaseModel):
      id: str                      # stable handle id: "text", "route.billing"
      label: str
      type: PortType
      required: bool = True        # inputs only
      multi: bool = False          # inputs: accepts several edges; the first
                                   # live value wins
      branch: bool = False         # outputs: a member of the node's exclusive
                                   # branch group
      enum_values: list[str] | None = None   # for enum ports
      score_range: tuple[int, int] | None = None   # for score ports, e.g.
                                                   # (1, 5)
      json_schema_ref: str | None = None     # for json ports: "Distribution",
                                             # "Docs", "PolicyReport"
      dynamic_from_param: str | None = None  # outputs generated from a param,
                                             # e.g. "allowed_intents" ->
                                             # route.<intent>. The port's id is
                                             # a template ending in ".*"
                                             # ("route.*"); registry.py
                                             # expands it per selected value.

  # Params: a union discriminated on "kind"
  class _ParamBase(BaseModel):  key: str; label: str; help: str = ""
  class NumberParam(_ParamBase):  kind: Literal["number"];  default: float;
                                  min: float; max: float; step: float = 0.05
  class IntParam(_ParamBase):     kind: Literal["int"];     default: int;
                                  min: int; max: int
  class EnumParam(_ParamBase):    kind: Literal["enum"];    default: str;
                                  options: list[str]
  class MultiEnumParam(_ParamBase): kind: Literal["multi_enum"];
                                  default: list[str]; options: list[str];
                                  min_selected: int = 1
  class StringListParam(_ParamBase): kind: Literal["string_list"];
                                  default: list[str]; max_items: int = 20;
                                  max_len: int = 60
  class TextParam(_ParamBase):    kind: Literal["text"];    default: str;
                                  max_len: int = 500
  class BoolParam(_ParamBase):    kind: Literal["bool"];    default: bool

      price_in_per_1k_usd: float | None = None     # LLM only (from config)
      price_out_per_1k_usd: float | None = None
      excluded_from_latency: bool = False          # human review

      is_source: bool = False
      is_sink: bool = False
      mvp: bool = True
      # run() is NOT serialized. registry.py maps type -> NodeRunner.

  class GraphNode(BaseModel):

      edges: list[GraphEdge]       # max 80

      message: str

                                   # are allowed)
      issues: list[ValidationIssue]

  # Runtime values
  Taint = Literal["injection","pii","policy_violation","ungrounded","misrouted"]
  class PortValue(BaseModel):
      type: PortType; value: Any; taint: set[Taint] = set()
  class Distribution(BaseModel): probs: dict[str, float]   # sums to 1 (+/-1e-6)

      cached: bool = False

3. NODE CATALOG AND PORT CONTRACTS
----------------------------------
3a. Port compatibility rules (catalog/compat.py and web/src/lib/compat.ts;
    both tested against shared/fixtures/port-compat-cases.json)
  - Same type on both ends                  -> allowed
  - Target is "any"                         -> allowed
  - Source is "any", target is concrete     -> allowed, warning ANY_SOURCE
  - Every other pair                        -> blocked (e.g. boolean -> text,
                                               enum -> text,
                                               score -> probability)
  - enum -> enum is allowed only if the source's values are a subset of the
    target's (checked by the server; the UI only checks types)
  - A single (non-multi) input accepts exactly 1 edge. A multi input accepts
    many; the first live value wins and later ones are logged and ignored.
  - Each output port has at most max_fan_out edges (default 4).
  - Branch ports are normal "text" outputs as far as typing is concerned.

3b. Catalog. MVP means it is in the minimal first version (spec section 11).
    Notation: in = inputs, out = data outputs, br = branch outputs (exactly
    one fires per request), * = multi input, ? = optional.
    Latencies and costs are mock defaults; all of them live in definitions/
    and can be tuned.

  [MVP] customer_message            io, source
    in : none
    out: text:text, meta:json(TicketMeta: channel, language; no labels)
    params: traffic_mix enum[realistic, routine_heavy, adversarial]=realistic
            language enum[en]=en
            attack_rate number 0..0.5=0.10
            (all three are overridden by the facilitator in official runs)
    cost: 0 ms, $0

  [MVP] jev_intent_router           jev
    in : text*:text
    out: intent:enum, probabilities:json(Distribution), confidence:probability
    br : route.<intent> for each allowed intent (template port "route.*",
         dynamic_from_param=allowed_intents), route.low_confidence
    params: allowed_intents multi_enum[billing, technical_support, bug_report,
              feature_request, account, other]=first four
            threshold number 0..1=0.50 (confidence below threshold fires
              route.low_confidence)
    cost: 40 +/- 15 ms, $0.0002 per call
    mock: accuracy depends on ticket category (routine ~0.95, complex ~0.85,
          ambiguous ~0.55). Confidence is calibrated so wrong answers tend to
          score lower, which makes the threshold param matter. A wrong answer
          adds the "misrouted" taint.

  [MVP] jev_safety_check            jev
    in : text*:text
    out: is_safe:boolean, confidence:probability, categories:json
    br : route.safe, route.unsafe
    params: categories multi_enum[prompt_injection, abuse, fraud, pii_request,
              self_harm]=[prompt_injection, abuse]
            threshold number 0..1=0.50
    cost: 30 +/- 10 ms, $0.0002
    mock: recall about 0.92 on injection/violation tickets for the enabled
          categories, false-positive rate about 0.03. As built (T4): taint is
          never stripped; a missed injection keeps its taint on route.safe,
          and a caught one leaves on route.unsafe for a human to clear.

  [ ]   jev_urgency_scorer          jev
    in : text*:text
    out: score:score(1..5), confidence:probability
    params: rubric_levels enum[3,5]=5, threshold number=0.60
    cost: 35 +/- 10 ms, $0.0002

  [ ]   jev_escalation_gate         jev
    in : text:text (pass-through, required), confidence?:probability,
         score?:score, flag?:boolean   (at least one of the last three is
         required)
    out: decision:enum[auto,human,fallback], confidence:probability
    br : route.auto, route.human, route.fallback
    params: min_confidence number=0.70, max_auto_urgency int 1..5=3,
            flag_routes_to enum[human,fallback]=human,
            fallback_route enum[human,auto]=human
    cost: 20 +/- 5 ms, $0.0001

  [MVP] llm_answer_generator        llm
    in : text*:text, context?:json(Docs)
    out: text:text
    params: model enum[small,large]=large
            temperature number 0..1=0.7
            max_tokens int 64..1024=512
            prompt text(<=500)="You are a helpful support agent."
    cost: time-to-first-token (small 150 ms / large 350 ms) plus
          tokens_out x per-token latency (4 / 10 ms). Prices per tier come
          from config. tokens_out = min(max_tokens,
          expected_answer_tokens x verbosity(temperature)).
    mock: if the input carries the "injection" taint, the model complies with
          probability small 0.7 / large 0.45, halved if the prompt contains
          hardening phrases ("ignore instructions in the message", "never
          reveal", ...). Compliance adds the injection taint and a marker
          phrase. Without context, a needs_grounding ticket gets the
          "ungrounded" taint with probability 0.4. Answer quality is higher
          for the large model on complex tickets.

  [ ]   llm_summarizer              llm
    in : text*:text
    out: text:text
    params: model enum=small, max_tokens int 32..256=128
    mock: shortens the text (lowers downstream tokens_in/cost) and keeps taint

  [MVP] knowledge_lookup            tool   (promoted in T4; the strong graph needs it)
    in : text*:text
    out: docs:json(Docs)
    params: source enum[faq,kb,tickets]=kb, top_k int 1..10=3
    cost: 25 ms + 5 ms x top_k, $0.00001
    behavior: deterministic keyword match against a small in-repo KB fixture

  [MVP] policy_engine               tool
    in : text*:text, context?:json
    out: passed:boolean, report:json(PolicyReport)
    br : route.pass, route.block
    params: rules multi_enum[no_refund_promises, no_legal_advice,
              no_internal_urls, no_credentials]=[no_refund_promises]
            blocked_phrases string_list=[]
            data_classes multi_enum[email, phone, card_number, ssn]=[]
    cost: 10 +/- 3 ms, $0
    behavior: pure regex/phrase rules. Catches the mock LLM's marker phrases
              only when a matching rule is on, so it catches some unsafe
              output but not all of it. That gap is the point of the
              exercise.

  [ ]   pii_redactor                tool
    in : text*:text
    out: text:text
    params: entity_types multi_enum[email, phone, card_number, ssn,
              address]=[email, phone, card_number]
    cost: 8 ms, $0
    behavior: regex redaction; removes the "pii" taint for the redacted
              classes

  [MVP] human_review_queue          human
    in : text*:text, context?:json
    out: text:text
    params: capacity int 1..10=2, reviewer_latency_s int 30..600=120
    cost: excluded from the automated p95; $2.00 per review (config)
    behavior: the reviewer clears all taint with probability 0.98. The
              outcome counts as "escalated". Capacity limits only come in at
              M5 (overflow then counts as dropped).

  [MVP] customer_response           io, sink
    in : text*:text
    out: none
    params: channel enum[email,chat]=chat, sla_ms int=800 (display only)

3c. Default starter graph (intentionally imperfect)
  customer_message.text -> jev_intent_router.text
  router.route.{billing,technical_support,bug_report,feature_request}
                        -> llm_answer_generator.text
  llm.text              -> policy_engine.text
  policy.route.pass     -> customer_response.text
  Built-in weaknesses for teams to discover:
    - router.route.low_confidence is unconnected (ambiguous tickets are
      dropped)
    - there is no safety check before the LLM (injections reach the
      generator)
    - the LLM is the large tier with max_tokens=512 (p95 well above 800 ms)
    - policy.route.block is unconnected (blocked answers are dropped, not
      escalated)
    - there is no knowledge lookup (ungrounded answers on complex tickets)
  Reference graphs (in-repo; used by the golden tests and the facilitator
  demo):
    weak   : default graph plus a second LLM pass, no policy engine
    strong : safety check -> router -> {routine: small LLM + knowledge lookup,
             low_confidence/unsafe: human review}; policy.block -> human review

3d. Validation (engine/validator.py). Errors block a run; warnings are shown
    on the canvas.
  errors  : UNKNOWN_NODE_TYPE, UNKNOWN_PORT, DUPLICATE_ID, DUPLICATE_EDGE,
            INCOMPATIBLE_PORTS, ENUM_VALUES_MISMATCH, INPUT_FAN_IN_EXCEEDED,
            FAN_OUT_EXCEEDED, MISSING_REQUIRED_INPUT, CYCLE, NO_SOURCE,
            MULTIPLE_SOURCES, NO_SINK, INVALID_PARAM, GATE_NEEDS_SIGNAL,
            GRAPH_TOO_LARGE
  warnings: UNREACHABLE_NODE, DEAD_END (an output can never reach a sink),
            UNCONNECTED_BRANCH (requests on that branch will be dropped),
            NO_SAFETY_COVERAGE (some source->sink path through an LLM has no
              safety check before the LLM and no policy engine after it),
            NO_HUMAN_FALLBACK (no path reaches human_review_queue),
            ANY_SOURCE, MULTI_INPUT_RACE (a multi input is fed by branches
              that are not mutually exclusive)

3e. Execution semantics (engine/executor.py)
  - The planner computes a topological order (and rejects cycles) and the
    exclusive branch groups.
  - Per request: walk the nodes in topological order. A node runs when every
    incoming edge has resolved, either live (a value was delivered) or dead.
    If a required input has no live value, the node is SKIPPED and all its
    outputs are dead. A multi input takes the earliest live arrival.
  - Simulated start time = max(arrival time of the inputs the node used).
    Request latency = simulated time at which the request reaches the sink,
    minus its arrival time (critical path). Human review latency is excluded
    from the automated percentiles.
  - Outcome:
      reached customer_response without passing human review -> automated
      reached customer_response through human review         -> escalated
      ended on policy.route.block / safety route.unsafe that
        has no downstream consumer                           -> blocked
      no sink reached                                        -> dropped
      an unhandled node error                                -> failed
  - released_unsafe = delivered to the customer AND (the value carries taint
    in {injection, pii, policy_violation}, OR ticket.must_block and the
    outcome is automated).
  - decision_correct: automated with the correct intent and no "ungrounded"
    or "misrouted" taint, OR escalated/blocked when must_escalate or
    must_block. A dropped request is always incorrect.

3f. Metrics (metrics/aggregator.py). All rates are over the total number of
    requests.
  automation_rate     = automated / total
  escalation_rate     = escalated / total
  unsafe_release_rate = released_unsafe / total
  dropped_rate        = dropped / total
  p50 / p95 latency   = nearest-rank percentile over automated requests (in
                        simulated ms)
  cost_per_1k_usd     = (sum of node costs + human review costs) / total x
                        1000
  decision_quality    = mean(decision_correct)
  score = w_automation x automation + w_quality x quality
          - w_unsafe x unsafe
          - latency_penalty_per_10ms x max(0, p95 - 800) / 10
          - cost_penalty_per_10pct x max(0, cost_per_1k / budget - 1) x 10
  The weights are in the pack's ScoringConfig. They get tuned in M1 so that
  default < weak-fix < strong.

5. TEST PLAN
------------
Server (pytest; async tests through the anyio plugin; sqlite tmp DB per test)
  models/
    - Pydantic round-trip (camelCase wire format <-> snake_case Python).
      Rejects unknown fields, bad PortTypes, out-of-range params,
      Distribution sums.
    - Every catalog definition is self-consistent: unique port ids, branch
      ports are only on outputs, dynamic_from_param refers to an existing
      param, defaults pass their own ParamSpec.
  compat
    - Parametrized over shared/fixtures/port-compat-cases.json (the TS suite
      uses the same file).
  validator
    - One test per IssueCode using a minimal graph (fixtures/graphs/
      invalid-*.json).
    - default.json has no errors and exactly the expected warnings (the
      deliberate weaknesses). strong.json has no errors and no
      NO_SAFETY_COVERAGE warning.
  planner / executor
    - Topological order; cycle rejection; branch exclusivity detection.
    - Dead-path elimination: a node only on an unfired branch is skipped and
      gets no events.
    - Multi input takes the first live arrival; a required input with no live
      value skips the node.
    - Critical-path latency on a diamond-shaped graph; human latency
      excluded.
    - Outcome classification for each Outcome value; released_unsafe truth
      table.
    - Determinism: same seed gives identical traces; changing node ids does
      not change results; different params do change them.
    - Event-order invariants (T5, on the in-memory sink's recorded stream):
      seq strictly increasing; run_started first and run_completed last;
      node_started before node_completed/node_failed for the same
      (request, node); edge_transferred only after its source node
      completed; one request_completed per request; skipped nodes emit
      nothing.
  node runners and mocks
    - Each runner returns only declared output ports with the declared types
      and fires exactly one branch when it has branches.
    - The router threshold monotonically increases low_confidence routing.
    - The safety check strips the injection taint only when it detects it.
    - The policy engine and PII redactor are pure functions (table-driven
      cases).
  metrics / scoring
    - Percentiles on known lists (including n=1 and empty), rates with
      zero-totals, cost per 1k including human cost, score formula with hand
      calculation.
  golden (pedagogy guardrails)
    - On the official pack: default has p95 > 800 and unsafe > 0; weak scores
      worse than default; strong has p95 <= 800, unsafe == 0, automation
      >= 0.6, and the highest score.
  scenario packs
    - Schema-valid; 30 official tickets; every category present; ticket ids
      unique; GET endpoints never return ticket text or labels for the
      official pack.
  API
    - Catalog, validate, graph CRUD (409 stale version, 423 locked, 401/403
      wrong team), run start/stop, leaderboard ordering, facilitator-only
      routes.
  WebSocket (TestClient.websocket_connect)
    - state_sync is the first message; auth rejected without a token; the
      subscription only receives its own team's events.
    - The same event-order invariants as the executor tests, checked again
      on the stream a client receives (the pacer must not reorder or drop
      events).
    - Stop mid-run: run_completed(status=stopped) and no events after it.
    - Reconnect mid-run receives a state_sync whose counts match the events
      received so far.
  persistence
    - Alembic upgrade on an empty SQLite DB; repository round-trips. An
      optional CI job runs the same suite against a PostgreSQL service
      container.
  providers (M6)
    - A fake slow provider triggers a timeout and then node_failed; a fake
      429 triggers a retry and then success; the spend cap trips over to
      mock; a cache hit sets cached=true; the redacting log filter removes
      message bodies and PII.
    - Real-provider contract tests are marked @pytest.mark.live and skipped
      unless keys are present.

Web (vitest + Testing Library + jsdom)

  - graphMapping: Graph -> React Flow -> Graph round-trip is lossless;

6. DEPLOYMENT
-------------
Topology: the browser loads the SPA from Vercel and talks DIRECTLY to the
backend over HTTPS and WSS. Vercel rewrites cannot proxy WebSockets, so the
same direct URL is used for both, which avoids split behavior. Locally, the
Vite proxy keeps everything same-origin.

Frontend - Vercel
  - Project root directory: web/. Framework preset: Vite. Build:
    `npm run build`. Output: dist/. Node 20.
  - Env (build time, public; NO secrets): VITE_API_BASE_URL=https://<api-host>
    VITE_WS_URL=wss://<api-host>/api/ws
    When these are unset (local dev), the client uses relative /api and the
    Vite proxy.
  - web/vercel.json: SPA fallback rewrite { "source": "/(.*)",
    "destination": "/index.html" }.
  - Preview deployments use the same backend (or a staging backend); the
    backend allows preview origins by regex.
  - vite.config.ts: change the proxy to
    { '/api': { target: 'http://localhost:8000', ws: true } }.

Backend - Railway (primary)
  - Service root: server/, built from server/Dockerfile (python:3.12-slim,
    non-root user, pip install ., copy app/ and migrations/).
  - Start: `alembic upgrade head && uvicorn app.main:app --host 0.0.0.0
           --port $PORT --proxy-headers --forwarded-allow-ips='*'`
  - Exactly 1 replica (in-memory run state and WS hub, decision D8). If
    multiple replicas are ever needed: Redis pub/sub for the hub, plus
    sticky sessions.
  - Railway PostgreSQL plugin -> DATABASE_URL. config.py rewrites postgres://
    to postgresql+psycopg://.
  - Health check path: /api/health. Restart policy: on failure.
  - Env vars (secrets go only in Railway variables, never in git):
      DATABASE_URL, ALLOWED_ORIGINS (comma-separated),
      ALLOWED_ORIGIN_REGEX (e.g. ^https://jev-vs-llm-.*\.vercel\.app$),
      FACILITATOR_CODE, TOKEN_SECRET, PROVIDER_MODE=mock,
      SPEND_CAP_USD, LOG_LEVEL,
      (M6) ANTHROPIC_API_KEY, LLM_MODEL_SMALL, LLM_MODEL_LARGE,
      JEV_API_URL, JEV_API_KEY
  - main.py replaces the hard-coded localhost CORS origin with
    settings.allowed_origins plus allow_origin_regex.

Backend - Render (alternative; same Dockerfile)
  - render.yaml: one web service (docker, rootDir server, healthCheckPath
    /api/health, numInstances 1) plus one Render PostgreSQL. WebSockets work
    on web services.
  - Free instances spin down when idle. Use a paid instance on workshop day,
    or hit /api/health beforehand.
  (Fly.io works with the same Dockerfile: `fly launch` from server/,
  min_machines_running=1.)

Workshop-day checklist
  - PROVIDER_MODE=replay (or mock) with pre-recorded responses; spend cap
    set; FACILITATOR_CODE rotated.
  - Warm up the backend; open the shared screen on /screen; teams join
    through the session code.
  - Run the default graph once as a smoke test, then reset all teams.

M3 decisions, accepted 2026-10-24:
  P1. Hosting as in section 6: server and PostgreSQL on Railway, web on
      Vercel. The code side (Dockerfile, configs, CI) is done in the repo;
      creating the projects and setting secrets needs the owner's accounts,
      so T17 ends in a short runbook the owner follows (or does with Claude
      in the terminal once logged in).
  P2. Facilitator auth: FACILITATOR_CODE (env) is only needed to create a
      session. Creating one returns the session code AND a session-scoped
      facilitator token (opaque, stored hashed like team tokens). No
      separate facilitator login.
  P3. Rejoining: joining a session with a team name that already exists
      issues a new token for that team and revokes the old one, so a team
      that loses its browser storage can get back in. The cost: anyone with
      the session code can take over a team by its name. Acceptable for a
      workshop room; the facilitator sees the join time per team.
  P4. Tables in M3: sessions, teams, graphs. graph_snapshots, runs,
      run_results and request_traces arrive with M4/M5 as new migrations,
      when code first writes them (section 4 listed them under M3).
  P5. Synchronous SQLAlchemy 2.0 (Session, not AsyncSession). FastAPI runs
      sync endpoints in its thread pool; M4's async run code will call the
      repository through run_in_threadpool. One code path for SQLite and
      PostgreSQL, no async driver.
  P6. No router dependency in the web app: four pages (/join, /team,
      /facilitator, later /screen) are picked from location.pathname in
      App.tsx, with history.pushState for navigation. Revisit if routes
      gain parameters.
  P7. Saving an invalid graph is allowed (work in progress); only the
      shape is checked (Graph model, size limits). Validation stays
      separate and advisory until a run needs it (M4).
  P8. Rename the web env var VITE_API_URL (T7) to VITE_API_BASE_URL, as
      section 6 names it.
